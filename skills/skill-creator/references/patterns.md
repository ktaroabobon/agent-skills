## 自由度を task に合わせる

指示の細かさは、その作業の**壊れやすさ**で決める。

| 自由度 | 手段 | 使うとき |
|--------|------|---------|
| 高 | 散文の指針 | 複数の正解がある。文脈で判断が変わる |
| 中 | 擬似コード、パラメータつきスクリプト | 定石はあるが変化の余地がある |
| 低 | 引数の少ない具体的なスクリプト、hook | 壊れやすい。順序が決まっている。一貫性が要る |

崖沿いの細い橋には手すりを付け、広い野原では道を指定しない。**全部を低自由度で書くと、モデルが状況に合わせる余地を潰して質が落ちる。**

## 進行的開示

3 段階でロードされる:

1. `name` + `description` — 常時コンテキストにある
2. SKILL.md 本文 — 発火したときに入る(500 行以内を目安)
3. `references/` / `scripts/` — 必要になったときだけ

**SKILL.md には「何をどの順でやるか」と「どの資料をいつ読むか」だけを書く。** 詳細・変種・表は `references/` に出す。

分割の型:

| 型 | 構成 |
|----|------|
| 変種別 | `references/aws.md` / `gcp.md` / `azure.md` — 選んだものだけ読む |
| ドメイン別 | `references/finance.md` / `sales.md` — 質問に関係するものだけ読む |
| 詳細度別 | 本文に基本、`references/advanced.md` に応用 |

**参照は SKILL.md から 1 階層まで。** references から別の references へ深く辿らせない。100 行を超える reference には冒頭に目次を置く。

## 核となる原則を 1 つ置く

本文の冒頭に、そのスキルの判断をすべて決める原則を **1 つだけ**書く。手順の途中で迷ったとき、モデルはこの 1 文に戻って判断する。

| スキル | 核となる原則 | そこから導かれること |
|--------|-------------|-------------------|
| commit | 意味のある塊だけを commit する | 塊になっていなければ 0 コミットでよい |
| 自律ループ | 完了の単位はユーザーの目標。コミットは通過点 | 1 コミットできても止まらない |
| 成果物の仕上げ | 会話は制作の文脈であって成果物の内容ではない | 指示・制約・例示は成果物に写さない |

原則が 2 つ以上あるなら、衝突したときの優先順位まで書く。書けないならそれは原則ではなく手順。

## 判断の要になる用語を定義する

スキルの品質が 1 つの概念の解釈で決まるなら(「塊」「漏れ」「ズレ」「違反」)、その概念を **定義 + 満たすべき性質 + 具体例 + 混ぜてはいけない組み合わせ** で書く。「適切に分けて」だけでは、分け方がセッションごとに変わる。

```markdown
## 変更の塊とは
1 つの意図を完結させる変更の集合。単独で理解でき、レビューでき、メッセージで正直に説明しきれる。

例: 1 機能追加 / 1 バグ修正 / 挙動を変えないリファクタ / 1 件のドキュメント更新
混ぜない: リファクタと挙動変更 / 機能 A のテストと機能 B の修正 / 生成物とソース(同じ塊の出力でない限り)
```

## 判定と実装を分ける

レビュー・検査・検証をするスキルに書き込みツールを持たせると、「指摘して、ついでに直して、直した結果を自分で承認する」が起きる。

- 判定系スキルは `disallowed-tools: Write Edit` で書き込みを外す
- サブエージェントに委譲するときも、渡すツールを `Read` / `Grep` / `Glob` に絞る
- 修正は別スキル / 別ターンに分ける

## 証拠主義

検査・レビュー系のスキルで最も効く規律。

1. **証拠(`file:line` + 逐語抜粋)を伴わない指摘を出させない。** 裏の取れない懸念は「notes」に隔離する
2. **「実装されていない」と「見つけられなかった」を区別する。** 後者は違反ではない。混同すると偽陽性が量産される
3. **「そもそも該当機能が無い」は N/A として明示する。** 「該当なし」を「準拠」と書かない
4. **重大度は根拠の強さで決め、最後まで保存する。** 「規格にこう書いてある」と「業界がそうしている」を混ぜない

偽陽性 1 件でレポート全体の信頼が落ちる。**重い指摘は出力前に実地確認する手順を入れる。**

## ゲートと自己正当化表

「検討したかどうか」が結果を左右する項目は、**表にして「使う / 使わない + 理由」を書かせる**。書かせないと、たいてい素通りする。

```markdown
| 機能 | 使う? | 理由 |
|------|:----:|------|
| hooks | ✅ | 生成物への Write を PreToolUse でブロックする |
| context: fork | ✗ | 会話の文脈が必要なので隔離すると使えない |
```

完了主張の前に置くチェックリストも同じ発想。**「〜した」と書かせるより「証拠はどこか」を書かせる。**

## 分類してから行動する

要素ごとに「消す / 残す」「直す / 直さない」を判断させると、基準がぶれる。**先に全要素をカテゴリに分類させ、カテゴリごとの扱いを固定する。**

```markdown
各記述を次のどれかに分類する:
1. 読み手が本当に必要とする内容 → そのまま残す
2. 設計には影響すべきだが見えてはいけない文脈 → 構成・語調・既定値に反映し、文としては消す
3. 会話の残滓 → 消す
```

分類が先にあると、「2 を 1 として残した」「3 を消しすぎた」を個別に指摘できる。

## 検出パターンを併記する

原則(「制作過程を漏らさない」)だけでは見落とす。**目視・grep で引っかかる表層パターン**を列挙する。

| 原則 | 表層パターン |
|------|-------------|
| 制作過程を漏らさない | 「ご要望どおり」「ユーザーの指示により」「今回は〜しない」「前のバージョンと違い」「制約があるため」 |
| 途中経過を commit しない | `chore: 作業途中` `fix: 一部修正` `wip` |
| AI 署名を入れない | `Co-Authored-By:` `🤖 Generated with` `noreply@anthropic.com` |

ただし**機械的に消すな**とも書く。パターンは発見のためで、残すかどうかは読み手に必要かで決める。判断なしに消してよいものは hook にする(→ [hooks.md](hooks.md))。

## 「何もしない」を正当な結果にする

副作用のあるスキル(commit / 投稿 / 修正 / 指摘)は、**行動しないのが正解になる条件**を明示する。書かないと、モデルは「呼ばれたからには何かする」方向に倒れ、`chore: 作業途中` や根拠の薄い指摘を生む。

- 「塊になっていない変更は commit しない。結果として 0 コミットでもよい」
- 「証拠のない懸念は指摘に出さず notes に隔離する」
- 「ズレが無ければ『該当なし』と報告して終わる」

0 件のときに**何を報告するか**までセットで書く(→ [出力形式を固定する](#出力形式を固定する))。

## 出力形式を固定する

出力の形が決まっているなら、テンプレートを本文か `references/` に置いて「この構成で出す」と指示する。

```markdown
## レポート構成
1. サマリ(件数マトリクス)
2. 検査スコープ
3. 優先度つき修正ロードマップ
4. 指摘詳細
5. 判定不能・該当なし
```

「該当が 0 件の節も『該当なし』と 1 行書いて残す」まで指定すると、**何を見て何を見ていないか**が読み手に伝わる。

### 行動系スキルの最終報告

レポートだけでなく、**行動するスキルの最終報告も固定する**。欄が無い項目は黙って省略される。

- やったこと(作成したコミット・投稿した内容・変更したファイル)
- **やらなかったことと理由**(意図的に残した変更、見送った指摘)
- 実行した検証コマンドと結果。**実行していないならその旨**
- 0 件だったならその事実と理由

## 制作過程を成果物に漏らさない

ユーザーが作業中に与えた制約・例示・修正指示は、**成果物の設計に反映するものであって、成果物に書くものではない**。読み手は会話を見ていない。

| ✗ 漏れている | ⭕ 設計に溶けている |
|-------------|-------------------|
| 「本ガイドでは Git や CLI ツールを使いません」 | 「プロジェクトフォルダは Google Drive で共有する」 |
| 「X については言及しません」 | X が存在しない構成にする |
| 「初心者向けに書きました」 | 用語を定義し、手順を細かく刻む |
| 「ご指摘を受けて〜に変更しました」 | 最初からそうだったように書く |

成果物を出すスキルには、あわせて次を書く:

- **成果物そのものを先に出す。** 「〜を削除しました」「こちらが修正版です」といった作業報告を前置きしない。報告は求められたときだけ、成果物の後に付ける
- 会話中の例は**意図を読み取るための材料**であり、成果物に写す内容ではない

SKILL.md 自身にも当てはまる。本文に「この節は〜の指摘を受けて追加した」のような経緯を書かない。

## 自律ループの止まり方

複数サイクル回すスキルは、モデルが早く止まる傾向に対抗する必要がある。**「止まる理由にならないもの」と「止まる条件」を両方列挙する。** 片方だけだと、列挙しなかった側で判断がぶれる。

```markdown
次の理由だけでは止まらない:
1 ステップ完了 / 1 コミット作成 / テストが一部通った / 計画の項目が尽きた / 残りが整理・文書化だけ

止まるのは次のどれか:
目標を達成し検証した / ユーザー入力なしに解けないブロッカー / 認証・課金・破壊的操作が要る / 安全に進められない状態
```

最終回答の直前に「ユーザー入力なしで進められる次の行動がまだあるか」を問わせ、あるなら続けさせる。

## 並列委譲 → 集約 → 偽陽性除去

独立に検査できる観点が複数あるなら、観点ごとにサブエージェントを分ける。

1. **共有コンテキストを先に 1 回だけ作る**(対象ファイル一覧・環境情報)。各エージェントに探索をやり直させない
2. **1 エージェント = 1 観点。** 「他の観点は扱うな」と明示する
3. **出力スキーマを固定する**(JSON 1 ブロックのみ、散文禁止)
4. **オーケストレータが集約時に検証する。** 重複排除、重い指摘の実地確認、低信頼の格下げ
5. **並列が使えない環境向けの逐次手順を必ず併記する**

サブエージェントの出力をそのまま結果にしない。**集約フェーズが品質の要。**

## ルールの置き場所

同じ内容でも、置き場所で効き方が変わる。

| 置き場所 | 向いているもの | 例 |
|---------|-------------|-----|
| CLAUDE.md / AGENTS.md | 常時効かせたい**短い**原則(数行) | 「成果物に会話のメタ情報を混ぜない」 |
| スキル本文 | 呼ばれたときだけ要る手順・定義・チェックリスト | 分類手順と検出パターン、塊の定義 |
| hook | 指示では守られない禁止事項 | AI 署名の混入、生成物の手編集 |

**CLAUDE.md に短く、スキルに詳しく**の二段構えは有効。CLAUDE.md に手順まで書くと毎ターン読まれてノイズになり、スキルだけに書くと発火しなかったとき何も効かない。

## 書き方

- **命令形で書く。** 「〜する」「〜しない」
- **理由を書く。** 大文字の MUST を並べるより「なぜそれが重要か」を説明したほうが守られる。`ALWAYS` / `NEVER` を書きたくなったら、まず理由に言い換えられないか考える
- **例を出す。** 抽象的な説明 3 行より before/after 1 組
- **「やらないこと」を書く。** スキルの境界が曖昧だと誤発火する
- **Claude は既に賢い前提で書く。** 一般知識の説明はトークンの無駄。**そのスキル固有の、Claude が知り得ない情報**だけを書く
- **特定の例に過剰適合させない。** 手元の 2〜3 例だけで動く指示は、実運用の 1 万件目で壊れる

## アンチパターン

| アンチパターン | なぜダメか |
|--------------|-----------|
| スキル内に `README.md` / `CHANGELOG.md` を置く | エージェント向けでない文書はノイズ。スキルは「実行に要るもの」だけ |
| 「いつ使うか」を本文に書く | 本文は発火後にしか読まれない。`description` に書く |
| 同じ情報を SKILL.md と references の両方に書く | 更新時にズレる。どちらか一方に置く |
| 巨大な 1 枚の SKILL.md | 毎回全部コンテキストに載る |
| 参照されない `references/` | 存在しないのと同じ |
| 検証していないスクリプト・hook を同梱する | 動かないものを配ることになる。必ず実行して確かめる |
| 実在しないコマンドを手順に書く | 一度でも外すと以後の指示全部が疑われる。書いたコマンドは実行確認する |
| 禁止事項を本文にだけ書く | 守られないことがある。hook にできないか検討する(→ [hooks.md](hooks.md)) |
| 全リポジトリ向けスキルに特定リポジトリの例を入れる | `feat: writer-profile MVP を追加` のような例は、そのドメイン語を持たないリポジトリでも真似される。例は汎用語で書くか、`git log` から拾わせる |
| 複数スキルに同じ規約を全文複製する | 片方だけ直って乖離する。単独インストールのために複製するなら、SKILL.md にその理由と「直すときは両方」を書く |
| 成果物の前に作業報告を置く | 読み手が欲しいのは成果物。報告は求められたときだけ後ろに付ける |
