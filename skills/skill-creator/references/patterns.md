## 自由度を task に合わせる

指示の細かさは、その作業の**壊れやすさ**で決める。

| 自由度 | 手段 | 使うとき |
|--------|------|---------|
| 高 | 散文の指針 | 複数の正解がある。文脈で判断が変わる |
| 中 | 擬似コード、パラメータつきスクリプト | 定石はあるが変化の余地がある |
| 低 | 引数の少ない具体的なスクリプト、hook | 壊れやすい。順序が決まっている。一貫性が要る |

崖沿いの細い橋には手すりを付け、広い野原では道を指定しない。**全部を低自由度で書くと、モデルが状況に合わせる余地を潰して質が落ちる。**

## 進行的開示

3 段階でロードされる:

1. `name` + `description` — 常時コンテキストにある
2. SKILL.md 本文 — 発火したときに入る(500 行以内を目安)
3. `references/` / `scripts/` — 必要になったときだけ

**SKILL.md には「何をどの順でやるか」と「どの資料をいつ読むか」だけを書く。** 詳細・変種・表は `references/` に出す。

分割の型:

| 型 | 構成 |
|----|------|
| 変種別 | `references/aws.md` / `gcp.md` / `azure.md` — 選んだものだけ読む |
| ドメイン別 | `references/finance.md` / `sales.md` — 質問に関係するものだけ読む |
| 詳細度別 | 本文に基本、`references/advanced.md` に応用 |

**参照は SKILL.md から 1 階層まで。** references から別の references へ深く辿らせない。100 行を超える reference には冒頭に目次を置く。

## 判定と実装を分ける

レビュー・検査・検証をするスキルに書き込みツールを持たせると、「指摘して、ついでに直して、直した結果を自分で承認する」が起きる。

- 判定系スキルは `disallowed-tools: Write Edit` で書き込みを外す
- サブエージェントに委譲するときも、渡すツールを `Read` / `Grep` / `Glob` に絞る
- 修正は別スキル / 別ターンに分ける

## 証拠主義

検査・レビュー系のスキルで最も効く規律。

1. **証拠(`file:line` + 逐語抜粋)を伴わない指摘を出させない。** 裏の取れない懸念は「notes」に隔離する
2. **「実装されていない」と「見つけられなかった」を区別する。** 後者は違反ではない。混同すると偽陽性が量産される
3. **「そもそも該当機能が無い」は N/A として明示する。** 「該当なし」を「準拠」と書かない
4. **重大度は根拠の強さで決め、最後まで保存する。** 「規格にこう書いてある」と「業界がそうしている」を混ぜない

偽陽性 1 件でレポート全体の信頼が落ちる。**重い指摘は出力前に実地確認する手順を入れる。**

## ゲートと自己正当化表

「検討したかどうか」が結果を左右する項目は、**表にして「使う / 使わない + 理由」を書かせる**。書かせないと、たいてい素通りする。

```markdown
| 機能 | 使う? | 理由 |
|------|:----:|------|
| hooks | ✅ | 生成物への Write を PreToolUse でブロックする |
| context: fork | ✗ | 会話の文脈が必要なので隔離すると使えない |
```

完了主張の前に置くチェックリストも同じ発想。**「〜した」と書かせるより「証拠はどこか」を書かせる。**

## 出力形式を固定する

出力の形が決まっているなら、テンプレートを本文か `references/` に置いて「この構成で出す」と指示する。

```markdown
## レポート構成
1. サマリ(件数マトリクス)
2. 検査スコープ
3. 優先度つき修正ロードマップ
4. 指摘詳細
5. 判定不能・該当なし
```

「該当が 0 件の節も『該当なし』と 1 行書いて残す」まで指定すると、**何を見て何を見ていないか**が読み手に伝わる。

## 並列委譲 → 集約 → 偽陽性除去

独立に検査できる観点が複数あるなら、観点ごとにサブエージェントを分ける。

1. **共有コンテキストを先に 1 回だけ作る**(対象ファイル一覧・環境情報)。各エージェントに探索をやり直させない
2. **1 エージェント = 1 観点。** 「他の観点は扱うな」と明示する
3. **出力スキーマを固定する**(JSON 1 ブロックのみ、散文禁止)
4. **オーケストレータが集約時に検証する。** 重複排除、重い指摘の実地確認、低信頼の格下げ
5. **並列が使えない環境向けの逐次手順を必ず併記する**

サブエージェントの出力をそのまま結果にしない。**集約フェーズが品質の要。**

## 書き方

- **命令形で書く。** 「〜する」「〜しない」
- **理由を書く。** 大文字の MUST を並べるより「なぜそれが重要か」を説明したほうが守られる。`ALWAYS` / `NEVER` を書きたくなったら、まず理由に言い換えられないか考える
- **例を出す。** 抽象的な説明 3 行より before/after 1 組
- **「やらないこと」を書く。** スキルの境界が曖昧だと誤発火する
- **Claude は既に賢い前提で書く。** 一般知識の説明はトークンの無駄。**そのスキル固有の、Claude が知り得ない情報**だけを書く
- **特定の例に過剰適合させない。** 手元の 2〜3 例だけで動く指示は、実運用の 1 万件目で壊れる

## アンチパターン

| アンチパターン | なぜダメか |
|--------------|-----------|
| スキル内に `README.md` / `CHANGELOG.md` を置く | エージェント向けでない文書はノイズ。スキルは「実行に要るもの」だけ |
| 「いつ使うか」を本文に書く | 本文は発火後にしか読まれない。`description` に書く |
| 同じ情報を SKILL.md と references の両方に書く | 更新時にズレる。どちらか一方に置く |
| 巨大な 1 枚の SKILL.md | 毎回全部コンテキストに載る |
| 参照されない `references/` | 存在しないのと同じ |
| 検証していないスクリプト・hook を同梱する | 動かないものを配ることになる。必ず実行して確かめる |
| 実在しないコマンドを手順に書く | 一度でも外すと以後の指示全部が疑われる。書いたコマンドは実行確認する |
| 禁止事項を本文にだけ書く | 守られないことがある。hook にできないか検討する(→ [hooks.md](hooks.md)) |
