判定の凡例: ❌ = MUST が 1 件以上 / ⚠️ = SHOULD または DEFACTO のみ / ✅ = 指摘なし / — = `not_applicable` / ? = `not_found`

**重大度の意味**(詳細は skills/openapi-rfc-compliance/checks/README.md):

- `MUST` — RFC の MUST/MUST NOT 違反。**仕様違反**
- `SHOULD` — RFC の SHOULD / BCP の推奨に反する。または標準があるのに採用していない
- `DEFACTO` — 標準は無いが業界慣行から逸脱している
- `INFO` — 情報提供。現時点で誤りではない

## 3. 修正ロードマップ

優先度順。上から着手する。

| # | 優先度 | rule_id | 内容 | breaking | 工数 | 該当 |
|---|--------|---------|------|----------|------|------|
| 1 | 🔴 MUST / 非破壊 | ERR-001 | | false | S | `api/openapi.yaml:412` |
| 2 | 🔴 MUST / 破壊的 | | | true | M | |
| 3 | 🟠 SHOULD | | | | | |
| 4 | 🟡 DEFACTO | | | | | |
| 5 | ⚪ INFO | | | | | |

並び順: `MUST かつ breaking:false` → `MUST かつ breaking:true` → `SHOULD` → `DEFACTO` → `INFO`。同順位内は工数の小さい順。

{{breaking: true の指摘がある場合はここに一文: 「破壊的変更を含む修正は、`Deprecation` / `Sunset` ヘッダで告知してから段階移行してください(→ 6.x 廃止告知)。」}}

## 4. 指摘詳細

領域ごと、重大度の高い順。

### 4.1 エラーレスポンス (RFC 9457)

#### `ERR-001` [MUST] problem+json の status が HTTP ステータスコードと一致していない

| | |
|---|---|
| 根拠 | RFC 9457 §3.1(Generators MUST use the same status code in the actual HTTP response) |
| 証拠 | `api/openapi.yaml:412` — `status: 400` |
| 現状 | 404 応答のスキーマ example が `status: 400` を返している |
| あるべき姿 | problem details の `status` は実際の HTTP ステータスコードと同一 |
| breaking | false |
| 工数 | S |
| 確認 | ✅ 実地確認済(Phase 3) |

```diff
- status: 400
+ status: 404
```

（以降、同じ書式で繰り返す）

## 5. 判定不能・該当なし

| 領域 | status | 理由 |
|------|--------|------|
| 廃止告知 | `not_applicable` | 非推奨のエンドポイントが存在しない |
| レートリミット | `not_found` | アプリコード・nginx conf・Terraform を確認したが制限の実装を特定できなかった |

**`not_found` は「準拠している」ことを意味しない。** 追加調査の対象。
